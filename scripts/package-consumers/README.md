# NuGet consumer validation

Run `./validate-packages.ps1` from the repository root with PowerShell and the .NET 10 SDK. The default Windows solution covers all active public libraries and requires the Windows desktop targeting pack. Pass `-solutionPath 'src/Sphere10.Framework (CrossPlatform).sln'` to validate that solution instead.

The script evaluates each source project's `IsPackable` and `PackageId`, builds a temporary solution containing the public libraries, and packs the complete dependency graph with a unique `0.0.0-validation.*` version. It checks IDs, versions, README/icon/license/repository metadata, matching symbol packages, internal dependencies and compiler-analyzer layout.

The fixtures in this directory are copied into an external temporary workspace. Their generated projects use only `PackageReference`; repository project references, build properties and central package versions are unavailable. Source mapping pins framework IDs to the generated local feed. An empty package cache and exact unique versions prevent an existing public package from satisfying a missing local dependency. Third-party packages restore from nuget.org, so the first restore requires network access.

Five consumers cover distinct compatibility requirements:

- **Core** references pure Web and verifies that ASP.NET Core and desktop UI dependencies are absent from its restore graph.
- **Application** references only the Application package and compiles the shared application/plugin/block hierarchy, plugin builder, presentation contracts and logic. Its resolved dependencies and framework references must exclude ASP.NET Core, WinForms, WPF and the platform UI packages.
- **Libraries** references every non-desktop, non-ASP.NET package, including NUnit helpers and the generator. A partial property must compile from the packed `AutoDirty` analyzer.
- **Desktop** references the Windows packages and derives `WinFormsApplicationScreen` and builds a typed `IWinFormsApplicationPlugin` with the native plugin and block builders.
- **Web** references MVC and Blazor and uses `BlazorApplicationBuilder` for document branding and registers a `BlazorPlugin` through `BlazorPluginBuilder` and the `BlazorApplicationBlockBuilder`, `BlazorApplicationMenuBuilder` and `BlazorApplicationMenuItemBuilder` APIs. Its interactive ApplicationShell runs inside ThemeProvider with a ThemeSelector. The screen uses a typed BlazorGrid backed by local ListDataSource records with CRUD and paging capabilities; Edit opens buffered name and reference-picker editors, while Save and Cancel use the framework controller. The consumer builds and publishes, verifies static web assets and CSS isolation imports, then checks plugin navigation, themed grid HTML, MVC XML, theme CSS and JavaScript over HTTP. Required assets include the current grid and reference-picker modules, so their absence from the package fails validation.

The checks validate packaging, compilation, server rendering and static asset delivery. They do not exercise browser interactions or replace the NUnit suites. To inspect the generated app interactively, run `dotnet ./PackageConsumer.Web.dll --urls http://127.0.0.1:5188 --environment Production` from its `published-web` directory after validation. Choose a theme, select a row, click Edit, open the Related record picker, and confirm that Cancel preserves the source value while Save applies the selection. Changes last only for that screen instance.

Packages, generated projects, logs, published files and `validation.json` remain in the reported temporary directory for diagnosis. Workspace names are deliberately short to keep NuGet/Razor asset paths within Windows tooling limits. No package publishing or automatic file deletion occurs. The source build uses `BuildRevision=0`, preserving the local build counter. Use `pack.ps1` separately to create release packages after validation.

For a focused recheck against an existing generated feed, copy the updated files from `scripts/package-consumers/Web` into the reported workspace's `Web` directory, then run `dotnet build <reported-workspace>/Web/PackageConsumer.Web.csproj -c Release --no-restore` and `dotnet publish <reported-workspace>/Web/PackageConsumer.Web.csproj -c Release --no-restore -o <reported-workspace>/published-web`. Stop the generated host before rebuilding. This reuses the already packed libraries; run the validation script again when framework source changes must be included. The script runs no NUnit suites.
