# Object Spaces

Read [ObjectSpace practices](../../../docs/guidelines/patterns/object-spaces.md) and the [project guide](../../../src/Sphere10.Framework/ObjectSpaces/README.md) before implementation. They own the current API, persistence boundaries and limitations; do not duplicate their rules in another client skill tree.

## Select the actual path

- For schemas/builders/indexes, inspect [ObjectSpaceBuilder](../../../src/Sphere10.Framework/ObjectSpaces/Builder/ObjectSpaceBuilder.cs), [ObjectSpaceDefinition](../../../src/Sphere10.Framework/ObjectSpaces/ObjectSpaceDefinition.cs), and the affected dimension/projection attachment. Read the [serialization skill](../serialization/SKILL.md) when changing member layouts or serializers.
- For identity, enumeration or mutations, inspect [ObjectSpace](../../../src/Sphere10.Framework/ObjectSpaces/ObjectSpaceBase.cs) and [InstanceTracker](../../../src/Sphere10.Framework/ObjectSpaces/InstanceTracker.cs). Check saved versus provisional instances, physical recycled slots and cache identity.
- For durability/ownership, inspect [FileObjectSpace](../../../src/Sphere10.Framework/ObjectSpaces/FileObjectSpace.cs) or [MemoryObjectSpace](../../../src/Sphere10.Framework/ObjectSpaces/MemoryObjectSpace.cs); read [resource scopes](../../../docs/guidelines/patterns/resource-scopes.md). Reopen verifies persisted values; cached reads alone do not.
- Preserve current store lifetime thread affinity: permanent dimension streams retain locks. Create/use/dispose on one owner thread; responsive UI sessions dispatch to a dedicated worker rather than switching the same store between arbitrary thread-pool calls.
- For a UI consumer, inspect the existing [ObjectSpace screen](../../../utils/Sphere10.Framework.Utils.WinFormsTester/Screens/ObjectSpaceScreen.cs) and its real registration in the [WinForms tester](../../../utils/Sphere10.Framework.Utils.WinFormsTester/README.md). Preserve its scenarios when changing the consumer. Select [crud-grid](../crud-grid/SKILL.md) or [data-source](../data-source/SKILL.md) when the requested change uses those abstractions.
- For performance, read the [ObjectSpace suite](../../../utils/Sphere10.Framework.Utils.Profiler/ObjectSpaces/README.md), [study workflow](../../../utils/Sphere10.Framework.Utils.Profiler/Studies/README.md) and [lab factory/models](../../../utils/Sphere10.Framework.Utils.Profiler/ObjectSpaces/Lab/README.md), all within the general profiling project. Select the actual backend, capabilities, dataset and mix; inspect the plan before execution, retain verified samples, and confirm shortlisted interactions through independent BenchmarkDotNet launches. The suite documents lookup locality, payload variability/resizing, category selectivity/skew and mutation controls. The current benchmark schema is PayloadOnly; DeveloperLab is retained only for factory/manifest fixture coverage and is rejected by benchmark settings. Follow the central [profiling practices](../../../docs/guidelines/patterns/object-spaces.md#profile-real-work) for comparison boundaries and evidence requirements.

## Verify the change

Extend the existing [ObjectSpace fixtures](../../../tests/Sphere10.Framework.Tests/ObjectSpaces) for core changes. Cover changed key shapes, indexed/nonindexed updates, duplicates, deleted holes, reopened identity, custom order and file commit/rollback where relevant. Use the [profiling fixtures](../../../tests/Sphere10.Framework.Utils.Profiler.Tests/README.md) for lab configuration, workload persistence and recorded study evidence; use native fixtures for changes to the existing screen consumer. Run affected NUnit fixtures and an appropriate profiler smoke workload; report actual evidence and preserve the distinction between correctness, screening and confirmed performance results.

For configuration work, read the [new-store defaults and existing-store contract](../../../src/Sphere10.Framework/ObjectSpaces/README.md#new-store-defaults-and-existing-storage) and [central constant owners](../../../src/Sphere10.Framework/Sphere10Defaults.cs). Existing-store examples must declare `WithIndexBTreeOrder(originalOrder)` and preserve original file cluster/page settings; do not replace an unknown original order with the current default. Verify both retained-store refusal without mutation and legitimate same-target reuse. Use the constant-backed `framework-defaults` profiling preset to replay current defaults; historical baseline/sweep controls stay independent. Keep garbage collection out of ordinary durable graph claims until its current persistence/cycle limitations are repaired and tested. Domain comparer behavior also needs index-specific tests. The project guide documents these boundaries and must be updated when they change.

When changing the profiling lab schema, increase its factory's `SchemaVersion` for serialized-member, dimension-order or index-layout changes. Preserve complete configuration manifests and explicit migration/replacement decisions for existing files. Version 2 declares PayloadOnly/DeveloperLab; legacy version 1 maps only to the original unchanged payload dimension.
